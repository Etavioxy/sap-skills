# Goals Gate Approver

## 目标

强制执行以下闭环：

1. 更新约束并调整方案。
2. 先做冲突检查再输出方案。
3. 每次完整方案后必须附带 Track。
4. 约束撤回时删除对应条目。

## 工作流

### 1) 确保 User Goals 章节存在

- 位置：项目 `AGENTS.md`（默认项目根，不限制根，可在子目录层级）的 `## User Goals` 章节（默认文件末段）。
- 目标层级无 `AGENTS.md`：创建文件 + 该章节骨架 + 章节头引用；其他章节留待 agent 按项目起草，不臆造项目约束。
- 已有 `AGENTS.md`：只补建缺失的该章节，不动其他章节。
- 约束一条一行，保持原子化和可核对。
- 章节头引用：`> 查看/修改 此章节 前请 invoke [[goals-gate-approver]]`。

### 2) goals 条目写作规范

goals 条目必须是"稳定的领域原则"，不是"会过期的动作细节"。它描述某种常驻的判别方式：在什么语境下做什么、不做什么、怎么取舍，跨版本、跨计划、跨阶段都成立。

Good：
- 用原则的方式编写，清晰说明概念的界限，如 CLI 层禁止调用底层原语。
- 用 `N` `<name>` `xxx` 这类抽象形态描述版本号、名称、标识符等易变量，特殊格式附上如 snake-case 的限定。
- 限定于某领域的条目，用"(模块名)"标注归属，如 `(模块名) 约束内容`。用半句话说明限制阶段或进入条件。

Bad：
- struct A 必须包含 x 个具体字段，Foobar.abc 的长度必须小于 NN 行——细节随实现演化就过时，不应限制实现。
- 在条目里写死"某一代版本""某个计划名""某个阶段"——一旦到了下一代或新计划，这条就不成立了。
- 没有前提条件，直接写"修改前必须..."——影响全局决策。

### 3) 先同步约束（强制）

- 用户要求写入 usergoals 时，必须先更新该章节，再输出新方案。
- 新约束：新增条目或精确补充到对应条目。
- 变更约束：当新约束与已有条目冲突时，必须打出 goals 原文，向用户说明冲突点，**需要用户确认后才能替换**，不得直接覆盖。
- 新增约束时必须同时兼顾**保留用户约束原句和完整表述上下文**，但不使用 `用户原句："…"` 引文格式。

### 4) 撤回约束处理（强制）

当用户撤回约束时：

- 删除该章节对应条目。
- 删除依赖该条约束而存在的冗余条目。
- 不得自动改写成"相反约束"，除非用户明确新增了反向要求。

### 5) 方案冲突检查（强制）

每次方案输出前，必须对照 AGENTS.md 全部约束做冲突检查：

- `Pass`：符合项
- `Conflict`：冲突项（方案不符合约束，先改方案再输出）
- `Unknown`：信息不足项（先补信息，不得猜测）

同时检查：

- 是否新增了未被要求的抽象（接口/类型/流程层级）；若新增，需先标记为 `Conflict` 并收敛。
- 所有关键结构结论必须附代码证据；无证据不得输出结论。

### 6) 字词级修改意图处理（强制）

当用户要求"删除一句话中的部分词语/片段"或"只改某个词义"时：

- 必须按字词粒度修改，不得整句误删或整段替换。
- 必须保留未被要求删除的语义部分。
- 修改后需该条是否仍与其他约束无冲突。

### 7) 执行时发现破坏约束必须询问用户

- 执行时应该做到每一步完成都逐条核对一下约束正确性
- 一旦发现行为破坏了约束，必须停止执行，向用户询问意见

### 8) 方案输出后和执行后附 Track（强制）

每次方案后或者执行完成后都要附带 `Track`，可以包含几种类型：

- `关键约束`：本轮最高优先级约束
- `高频误区`：多次被用户要求的约束
- `文件级指标`：文件/代码文本硬指标（修改文件范围、关键约束词计数、验收相关计数）

## 禁止项

- 约束变更后，禁止保留旧的冲突条目。
- 没有冲突检查结论时，禁止输出新方案。
- 用户只要求"删除约束"时，禁止擅自改写为反向约束。
- 发现方案中包含未告知的新增抽象时，禁止直接推进方案。
- 用户要求字词级修改时，禁止按整句/整段粗粒度替换。
