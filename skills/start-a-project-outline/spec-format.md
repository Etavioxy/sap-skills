# spec.md 格式规范

`spec.md` 是项目的技术规格（SAP spec1 → spec2 阶段产物，随 src 持续修订，不是一次定稿）。

职责边界：技术选型 / 架构决策 / 模块结构 → `spec.md`；概念级推导 / 实现原则 → `docs/`；不在 `spec.md` 展开某概念的实现细节。

通用原则：不写版本号或版本归属；不写易变的状态标注（当前契约 / 待落地 / 待确认 / 待实测 / 未决 / 审查中），被取代的历史方案删除或在原文特殊标注历史；禁止写验收相关内容（验收基线 / 验收目标 / 通过标准）；未决事项不进 spec，留给对应域承接。

## 技术选型

选什么技术栈，为什么。表格：选型 / 理由，理由内联一句话。

## 技术决策 / 架构决定

按主题分组（`### 主题`），每条一行 bullet：决定 + 理由内联；不编号，不逐条分段论述。

一条 bullet 只装一个命题的一个决策——两件事拆两条。理由只写作用，技术细节、推导依据与证据链放 `docs/`，spec 内用引用衔接，可以用括号引用概念。

不写技术栈选择（归「技术选型」节），不写「分几层 / 有几类 / 有几种」盘点式概括（分层分组的清单归 `docs/`），不在括号里追加细节枚举、补充说明。

## 模块结构 + 目录布局

SAP structure 阶段的落点。ASCII 树开一段；一张树（本仓结构）。

## 可有的部分（按项目需要）

各项目差异很大，不强制统一：

- **初步 insight**——每条：认识 + 真实数据 + 设计后果。
- **最佳实践**——采纳的上游规则（框架官方 best practices 一类）；每条：规则 + 出处。
- **排除**——明确不选的方案 + 理由归纳对比。
- **风险**——可能出错的点 + 后果与方向，现在时陈述；风险是持久的决策输入，不是进度状态；风险消失时删除该行，已做决策覆盖的改写为普通决策条目。
- **时效**——只靠现状成立、会被上游改动判废的条目；判据：上游版本 / 工具 / 环境一变即删除该行。
