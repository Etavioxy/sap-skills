# docs/concrete-insight.md 格式规范

`docs/concrete-insight.md` 用**数据全景图**演示数据从产生到消费的完整链路（SAP spec1 > concrete-insight 阶段）。

定位：展示**全部数据流**——数据从产生到消费的完整链路，每一段标注真实可能数据和格式布局，节点用产物/模块名定位（链路经过什么，不写抽象）。回答「这条链路长什么样」，不写空洞抽象。
职责边界：concepts 是术语与概念定义；concrete-insight 是「具体链路演示」；docs 是「概念怎么实现」；concrete-insight 的数据格式依赖 spec 的技术决策。

## 内容组织

首节永远是**总览全景链**：一张图覆盖数据从产生到消费的全程，串联所有概念，节点标真实模块。

后续每一节是**主链上的一段**。标题写"这一段链路在干什么"，总结流程，不以概念名主导。小节也可以分各链入口、链间关系，嵌套画主链全景图。

- **数据格式布局**——表格或代码块展示数据的实际格式：来源位置、字段类型和布局、tag / 标识。可以是实测，也可以是设计推演——有具体支撑即可。
- **经过的代码模块 / 概念模块**——数据流过哪些代码模块或概念模块，在图中与正文标出并解释。
- **图 / 时序**——ASCII 图或时序块演示数据如何流动。
- **完整层级结构**——，用缩进树展示数据或模块的完整层级骨架，表现真实确认的部分，用省略号表示可扩充。
- **UI 布局**——涉及界面（窗口 / 面板 / 控件）时，用 ASCII 画出具体布局设想。

## 规则

- **以图表为主体**，每一节由「图 / 时序 / 表格 / 真实格式块」承担内容，**禁止成段的叙述文字**
- **图表要一眼可读**：选图型先问「读者扫一眼能不能看懂这段流程」；**禁止用明显不合适的方式描述一个流程**（拿并列表格讲有时序的迁移、拿层级树讲 UI 布局、拿列表讲有层级的树，都是禁止项）。
- **表格与列表不超过三行**：超三行即拆开、或改画成图。
- 不写「发现」「开放问题」「差距」「待解决」。
- 不写总结性质内容（结论 / 归纳 / 评价），不写反例和旧版本例子。
- 只能有实际内容：数据流本身 + 数据格式 + 经过的模块。
- **禁止展示非数据和伪代码的代码片段**：不贴实现代码，包括结构定义、函数签名、命令行，可以 JSON。
- 不写具体未编写的代码名、接口函数名、行号。
