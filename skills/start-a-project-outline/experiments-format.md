# experiments 格式规范

SAP experiments 阶段，每个实验是 `experiments/` 下的一份独立目录，内含 README.md 与验证产物；所有实验登记在 `experiments/index.md`。

## 验证产物

实验用来证明自己成立、也是交给用户验收的东西。**形式由实验自己选：**

- **case-runner 测试**——`cases.*` + `runner.*`，可运行、可复跑；细则见文末。
- **prototype**——一个跑得起来的原型。
- **录制**——视频或回放文件。
- 也可以按实验自己设计。

每种形式都要配一份**核对清单**——列出命题的关键路径，用验证产物逐条核对；case-runner 形式下它就是 `cases.*`。

形式定了，就像实验里的其他文件一样放在实验目录内，受命题独立性约束。

## experiments/ 路径结构

根目录下创建 `experiments/` 文件夹。子文件夹格式：`DD-kebab-case`（DD 为数字序号）。

每个实验是一个独立的 package（不依赖主仓库），随语言有自己的构建配置；代码文件可能在 `src/` 里，也可能直接在实验根目录。内含验证产物与 README.md：

```
experiments/DD-kebab-case/     ← 一个实验
├── <验证产物>                 ← case 代码 / prototype / 录制 / 其他
└── README.md                  ← 实验设计和结论
```

多个实验同处一个 git 仓库（monorepo）。

## 命题独立性

实验是一个能单独成立的命题，把它的目录整个拷出去，仍然跑得起来、读得通：

- **运行独立**：自带依赖声明与构建配置（形式随语言而定），不借用主仓库的依赖、配置或命令；跑法只用实验内的路径。
- **文档独立**：实验的所有文档——README、源码注释、页面标题——不出现主仓库的任何信息：仓库名与产品名、任何指向主仓库的路径、主仓库的命令与工具链，以及「移植进产物 / 正式页」这类只有主仓库语境才成立的说法。
- 实验内部互相引用只用相对本实验的路径。

## README.md

README 记录实验设计与结论。

- **structure**：ASCII 结构树开一段——一张树（本实验结构），每个节点右侧挂注释；树后接几条结构规则，写明哪类东西放哪、哪个目录是唯一落点。
- **验证产物表**：另起一表，三列「形式 / 产物 / 证明什么」；写证明什么，不写做了什么。
- **验收条件**：验证产物表的「证明什么」列是多条、多阶段的验收条件。
- **最小 takeover**：给出一个**最小代码产物**——下游（要接入这份产物的人）把它接起来最少要写的那点代码。受命题独立性约束，不写下游的路径与落点。

其余段落按需自取，不强制：假设 / 做法 / 结果 / 结论 / 跑法。

## experiments/index.md — 实验清单

列出距离实现 MVP 最值得 failfast 测试的实验。等用户确认后记录为 index.md。

- **格式**：三列表格（编号 / 实验名称 / 描述），描述只写实验目的/问题，一个实验一行。
- **表格下方**：每个实验一个 `## DD-name` 小节。

```
| 编号 | 实验名称 | 描述 |
|------|---------|------|
| 01 | <名称> | <目的/问题> |

## 01-<name>

- **状态**：<通过/失败>（<当前验收条件和状态原因>）
- **形式**：<case-runner / prototype / 录制 / 其他>
- **验收**：<人工/自动>    // 谁来验
- **结论**：<验证结果>
- **skip 项**：<未跑项及原因>
- **局限**：<已知局限>    // 实验测不到的真实环境
- **遗漏**：<遗漏>    // 未开始的实验不写遗漏、疑虑点
- **疑虑点**：<疑虑点>
```

`形式` 里的「其他」指实验自己设计的验证形式；**不能只写「其他」**，要把具体形式写出来。

## 细则：case-runner 测试

### cases.* — case 验收框架（代码文件）

- 根据用户的需要（命题），编写 case。
- `cases.*` ——代码文件，是可运行的验收，注意不是 `.md` 文档。
- `cases.*` 是一个文件——所有 case 及其 action（script）写在这一个文件里，不拆成多个脚本文件。
- 全部测试都要放在 `cases.*` 展示出来——直接用 cases 运行，不另建 `tests/` 目录或独立测试文件。

### caseenv（可选）

- caseenv 是 case 的运行环境，与 cases 同处（代码文件）。
- **可选**——只有需要**多个不同规模和特点**的环境时才声明。
- case 用 `envs` 声明它适用的 caseenv，可在一个或多个 caseenv 上验证。

### case 文件内部结构

每个 case 声明「一个场景下应该成立什么」。结构体 + 注释：

```
case <name> {
  type:     <case 类型>            // 不同类字段不同
  story:    <story 背景>           // 必选，用自然语言全部概括
  action:   <执行被测能力的动作序列> // 可选，通常为数组——调用 runner 提供的能力，按序执行
  scene:    <场景构造>              // 可选，构造验证场景
  data:     { ... }                // 一个序列化对象，runner 注入的输入数据，结构随 action 而定
  envs:     <caseenv 列表>         // 可选，此 case 适用的 caseenv
  expect:   <期望>                 // 可选，验证应成立的结果
  reason:   <说明>                 // 可选，case 的补充说明
  ...                             // 可自行补充
}
```

### runner.* — 验证执行（被 cases import 的函数库）

`runner.*` 是函数库。cases 会使用 runner 的能力。作用：

1. **提供 case 的 action 所需能力**——runner 暴露能力函数，case 的 `action` 数组引用它们执行被测功能。
2. **准备基础设施函数**——起/收环境（沙盒构造）、读执行日志、场景编排等。
3. **执行验证**——runner 提供 `run_case`（构造场景 → 执行 action → 核对 expect）；涉及多 caseenv 时按 case 的 `envs` 组合验证。
