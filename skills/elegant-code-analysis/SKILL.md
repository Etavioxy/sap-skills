# elegant-code-analysis

> **一致性 (Consistency) 是降低复杂性的强大工具。**
> —— John Ousterhout, *A Philosophy of Software Design* (Chap. 17 "Consistency")

改动是负债。改前先评估：评估要独立、要量标尺、要套模板；而贯穿这一切的核心原则是**一致性**——本质相同的东西，形状应当相同。

## 前置：分层理解（辅助工序）

动手评估前，先读代码理解系统的层：

- **读代码，理解概念（DDD）**：识别领域概念，不只盯着函数。
- **主动找到抽象层**：每层暴露什么、隐藏什么，职责边界在哪。

分层结论要**落地到文档**——分层理解难，不记会忘；文档是锚点，防漂移。

后续所有判断都建立在这个分层上：Blast Radius 的跨层维度、Consistency 的同构分析，都以分层为前提。

## Consistency（一致性 / 同构）

**本质相同的东西，形状应当相同。** 不同构的根源是：同一个概念被表达了两次、两种形态，迫使后续代码写分支/状态去弥合差异。

**多余分支不明显的陷阱**：单独看一处，永远看不出冗余——必须**对照两个形态**才看得见。这是需要付出努力的原因。

**可执行分析（4 步）**：
1. **找同形物**：这个改动涉及的概念，代码里还有没有"本质相同但形状不同"的另一个？
2. **问为什么不同**：历史原因 / 真实差异 / 意外漂移——只有真实差异配得上分支。
3. **算账**：弥合差异要写多少分支、状态、重复代码？
4. **决定**：同构化（合并形状，分支消失）vs 接受差异（写明理由，确认为真实差异）。

**判据一句话**：如果两个本质相同的东西需要不同的处理，先怀疑它们被设计得不同构，而不是急着写分支。

## 不同层级，不同抽象

**与 Consistency 互为镜像**：Consistency 管"同层内同构"，本节管"跨层间不同构"——一致性告诉你哪里该统一，层级差异告诉你哪里不该统一。

系统不是天然分层的。**层是抽象的聚类**：每个抽象隐藏一个细节域，共享隐藏目标的抽象聚成一"层"，层的边界即抽象边界。

推论链：
- 抽象的职责 = 隐藏一个细节域，暴露简化接口。
- 同细节域的抽象聚成层。
- 一层只有**隐藏了新东西**才配存在 → 透传层（原样转发、啥也不藏）是假层，删掉它复杂度不消失。
- 跨层引用 = 泄漏：上层用到下层的抽象，下层内部变化穿透上层 → 影响面放大。

**跨层检查——不能跨两层**：
- 健康依赖链是相邻层一跳一跳：A→B→C。
- 改动要从 A 直达 C（跨两层）→ 中间 B 形同虚设 → B 要么是透传假层，要么层级划错了。
- 跨两层 = 触碰 3 个细节域 + 中间层失效 → 影响面最坏。

## Blast Radius 度量

一个方案的影响面 = **受影响集合 × 影响性质**。度量从四个方面看：

- **改动行数**：改了多少行，落到哪些文件/函数。量级差异往往暴露真实风险（改 20 行 vs 改 2 行）。
- **正反向影响**：哪些场景变好、哪些场景变差。只报"好处"是作弊；必须列出受影响者的反向情况。
- **结构一致性**：改动是否符合原有代码结构。绕开原结构打补丁，短期行数少，长期是债。
- **跨层差异**：跨层改动会触碰多个抽象层，影响面天然比同层改动大——见「不同层级，不同抽象」。

**常见误判**：用"改动是否在某个领域内"判断风险，而不用"实际影响集合 × 性质"。全局调度入口看着"在领域内"，实际影响全量组件——这是最贵的误判。

## 评估手段

沿层级逐个深入分析：一个改动会落在哪些层（组件 / 调度 / 数据…），每一层在什么地方落地、受什么影响。逐层往下把足迹想全——只盯着改动起点，会漏掉它在其他层的落地。目标是**想全面**，不是想得多。

评估之前思考：

1. **我有没有被倾向带偏？** ——先按代码事实定，再对照他人倾向；倾向与事实冲突时要提出，别沉默。
2. **影响面多大？** ——见「Blast Radius 度量」。
3. **该套哪个权衡模板？** ——见下。

有多个候选设计时，**每个候选单独输出一份 blast radius 评估**——不可合并成一个笼统结论。合并会让某个候选的真实风险被平均数稀释。

**评估输出格式**（每个候选一份）：

```
Blast Radius — <候选名>
- 改动行数：约 N 行（落到哪些文件/函数）
- 正向影响：哪些场景变好
- 反向影响：哪些场景变差
- 结构一致性：是否符合原有代码结构（绕开打补丁？）
- 跨层情况：同层 / 跨一层 / 跨两层以上
```

## 权衡模板

每个模板是一段判断，长度随内容走；短一句，长几句。

- **显式类型 vs 运行时反推**：反推歧义大（空值、多反向分支）就显式声明；但显式有维护成本（挂载、防漂移），能用反推说清时别过度声明。

- **新增收集来源 vs 改全局调度入口**：新增来源不动现有路径，影响面小；但如果现有路径本身就是目标，改它才是对的——不要为了"不动现有代码"而绕远路。

- **复用现成路径 vs 另起炉灶**：复用省力，前提是现成路径方向对；方向错了（数据源不匹配、语义不符），复用是错上加错，这时候新建是对的。

- **抽象层 vs 堆代码**：未来有多个变体或数据源，抽象层划算；只有一个用途时，抽象是多余复杂度，直接改就好。
